# Spec Delta

## Purpose

Provides cryptographically secure random bytes, bounded integers, and version 4 UUIDs for keys, salts, and nonces, backed only by `node:crypto`.

## ADDED Requirements

### Requirement: Secure random bytes

The `random` capability SHALL provide `bytes` and `bytesSync` that return `length` cryptographically secure random bytes from `node:crypto` `randomBytes` (Node.js crypto documentation), as a `Buffer` by default or as text when an encoding is given.

#### Scenario: Default Buffer output

- **WHEN** a caller awaits `bytes(16)` or calls `bytesSync(16)` with no encoding
- **THEN** each call SHALL return a `Buffer` of 16 bytes, and two successive calls SHALL NOT return equal bytes

#### Scenario: Encoded text output

- **WHEN** a caller requests `bytes(16, 'hex')`
- **THEN** the call SHALL return a 32-character lowercase hexadecimal string decoding to 16 bytes

#### Scenario: Invalid length

- **WHEN** `length` is negative, non-integer, or not a safe number
- **THEN** both variants SHALL throw a `NodeCryptoError` with code `INVALID_ARGUMENT`

### Requirement: Encoded random bytes

`bytes` and `bytesSync` SHALL support `hex`, `base64`, and `base64url` output encodings per `shared-core` (Node.js `Buffer` encodings), and SHALL reject any other encoding value.

#### Scenario: Each supported encoding

- **WHEN** a caller requests `bytes(16, 'base64')` or `bytes(16, 'base64url')`
- **THEN** the call SHALL return text that strictly decodes under that encoding to 16 bytes

#### Scenario: Unsupported encoding

- **WHEN** a caller passes an encoding outside `hex`, `base64`, and `base64url`
- **THEN** the call SHALL throw a `NodeCryptoError` with code `INVALID_ARGUMENT`

### Requirement: Bounded random integers

The `random` capability SHALL provide `integer` and `integerSync` accepting an options object `{ min?, max }` that return a uniform integer in `[min, max)` from `node:crypto` `randomInt` (Node.js crypto documentation), where `min` defaults to `0` when omitted.

#### Scenario: Bounded result

- **WHEN** a caller requests `integer({ min: 1, max: 7 })`
- **THEN** the call SHALL return an integer `n` with `1 <= n < 7`

#### Scenario: Default minimum

- **WHEN** a caller requests `integer({ max: 10 })`
- **THEN** the call SHALL return an integer `n` with `0 <= n < 10`

#### Scenario: Empty or unsafe range

- **WHEN** `max <= min`, either bound is a non-integer or an unsafe number, or `max` is missing
- **THEN** both variants SHALL throw a `NodeCryptoError` with code `INVALID_ARGUMENT`

### Requirement: Version 4 UUIDs

The `random` capability SHALL provide a synchronous `uuid()` that returns an RFC 9562 Section 4.1 version 4 UUID string from `node:crypto` `randomUUID` (Node.js crypto documentation).

#### Scenario: UUID shape

- **WHEN** a caller calls `uuid()`
- **THEN** the call SHALL return a string matching RFC 9562 Section 4.1 `xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx` with variant bits `8`, `9`, `a`, or `b`

#### Scenario: Uniqueness

- **WHEN** a caller calls `uuid()` twice
- **THEN** both calls SHALL return well-formed version 4 UUIDs that are not equal

### Requirement: Variant parity with a random-output exception

`bytes`/`bytesSync` and `integer`/`integerSync` SHALL throw equal error codes for equal invalid inputs, and SHALL return equal shapes (same byte length, same integer bounds) for equal valid inputs; they SHALL NOT return identical random bytes because each call draws fresh entropy (NIST SP 800-90Ar1 Section 8). `uuid` SHALL remain synchronous only per the approved proposal exception to `shared-core` variant parity.

#### Scenario: Error parity

- **WHEN** async and sync variants receive the same invalid argument
- **THEN** both SHALL throw a `NodeCryptoError` with the same code

#### Scenario: Shape parity instead of value parity

- **WHEN** `bytes(16)` and `bytesSync(16)` are each called with valid inputs
- **THEN** both SHALL return 16-byte buffers without requiring byte equality

#### Scenario: No async UUID

- **WHEN** the `random` entry point is inspected
- **THEN** it SHALL expose a synchronous `uuid` and SHALL NOT expose `uuidSync` or an async `uuid`

### Requirement: Error message hygiene

Every error thrown by the `random` capability SHALL be a `NodeCryptoError` with a stable code and SHALL NOT include generated bytes or UUIDs in its message (follows `shared-core` error model).

#### Scenario: No secret echo

- **WHEN** any `random` call fails validation
- **THEN** the error message SHALL use a fixed description of the violated rule with no generated value interpolated

### Requirement: Approved cryptographic provider only

All `random` output SHALL come from the `node:crypto` CSPRNG (`randomBytes`, `randomInt`, `randomUUID` per the Node.js crypto documentation and NIST SP 800-90Ar1) and SHALL NOT use `Math.random` or any hand-rolled generator.

#### Scenario: No Math.random dependency

- **WHEN** `Math.random` is replaced with a constant during a `bytes(16)` call
- **THEN** successive calls SHALL still return differing buffers
